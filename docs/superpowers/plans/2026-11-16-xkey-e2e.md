# xkey Invalidation E2E Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Prove over real HTTP traffic that an xkey purge through the invalidation service removes exactly the tagged objects on every pod, with an exact `objectsPurged` count, on both flavor legs.

**Architecture:** No product change. `vinylprobe` gains a way to seed an object whose response carries an `xkey` header (it asks the echo backend through `X-Echo-Header`) and a `-purge-xkey` mode that posts to `/purge/xkey` and asserts the count. A new unclustered fixture with only xkey enabled carries items 1 to 6 in a rewritten `xkey-invalidation` test. Item 7 goes into `shard-routing`, whose fixture gets `xkey.enabled: true`.

**Tech Stack:** Go 1.26, chainsaw v0.2.12, kind v0.32.0 + `kindest/node:v1.36.1`, Calico v3.31.1, `ealen/echo-server:0.9.2`.

**Spec:** [cloud-vinyl#191](https://github.com/bluedynamics/cloud-vinyl/issues/191) (no separate design doc; the issue is the spec). Background: [#157](https://github.com/bluedynamics/cloud-vinyl/issues/157) gap 1.

## Global Constraints

- No change to how keys are set or purged: no edits under `internal/proxy`, `internal/generator`, `api/` (issue: "Not in scope").
- Soft key purges and BAN stay out of scope.
- `cmd/vinylprobe` and everything it imports must not depend on `k8s.io/*` (`hack/check-e2e-boundary.sh`). `_test.go` files in `internal/probe` may import `internal/proxy`; the boundary check builds without `-test`.
- chainsaw tests own Kubernetes state only: no `curl`/`wget`, HTTP goes through `vinylprobe`.
- Every test in `e2e/tests/` carries exactly one `metadata.labels.suite` (`hack/check-suite-labels.sh`). `xkey-invalidation` stays `full`, like `shard-routing`, which carries item 7.
- `--include-test-regex` needs the `chainsaw/` prefix, or it silently matches nothing and exits 0 (#63). Always confirm the summary reports the test as run.
- Every throwaway kind cluster runs with `--kubeconfig <scratchpad file>` and `KUBECONFIG` pointing at it. Never touch `~/.kube/config`. Docker context `default`.
- Commit prefixes: `test(probe):`, `test(e2e):`, `docs:`. goreleaser drops `docs`/`ci`/`chore` from release notes; `test` stays in, which matches past E2E work (#171, #174).
- Every commit and the PR body end with `Assisted-by: <model(s)>`. PR in English.

## Review Focus

1. **Default TTL expiry.** The echo backend sends no `Cache-Control`, so objects live for Varnish's default TTL of 120 s. If more than 120 s pass between a round's seed and its last check, a "cached" check fails for the wrong reason. Expected: every round seeds and checks within seconds. Pinned by Task 3's rule that each round's seed, before-check, purge and after-check sit in adjacent steps, and no object outlives its round.
2. **Re-seeding a path after a not-cached check.** The check's miss puts the object back in cache without keys (the check sends no `X-Echo-Header`). A later `-seed` on that path is a cache hit that tags nothing. Expected: every seeded object uses a path no earlier step has touched. Pinned by Task 3's object table, which gives `d1` and `d2` separate paths, and by the before-check after every seed, which fails loudly if a seed was a hit.
3. **One request naming two keys of the same object.** The proxy sends one `PURGE` per key. If vmod_xkey's hard purge leaves the object indexed until the expiry thread removes it, the second key counts it again, and `objectsPurged` reports 6 where 3 objects were removed. Expected: 3. Task 3's object `g` asserts the object is gone and records the count without asserting it. If it comes back as 6, that is a separate count-accuracy issue, outside #191.
4. **A partial broadcast read as success.** With one pod down, a 207 with known counts from the healthy pods would satisfy `-expect-purged 0`. Expected: failure. Pinned by `TestPurgeXkeyRejectsPartialBroadcast` (Task 1).
5. **Probe request body drifting from the proxy's decoder.** `proxy.xkeyRequest` is unexported, so a probe-side typo (`"key"` for `"keys"`) would only show up in CI as a 400. Pinned by `TestPurgeXkeyRequestIsWhatTheRealProxyDecodes` (Task 1), which drives the real `proxy.Server`.

- `purge.go`: `PurgeXkey` marshals a local `struct{ Keys []string `json:"keys"` }`, POSTs with `Content-Type: application/json`, and on HTTP 200 decodes `purgeResponse` (nil count on undecodable body, as in `Purge`). Any other status is an error naming the status and quoting up to 1 KiB of the body. Doc comment: Varnish's xkey branch answers 200 even when nothing matched, so the proxy answers 200 exactly when `status` is `ok` (`httpStatusCode` in `internal/proxy/broadcast.go`). Requiring 200 is what makes "status ok with objectsPurged 0" assertable, and it is why 207 is rejected here although `Purge` accepts it.
